# 商城能力路线图与实施规格

> 状态：P0 已实现并完成本地构建验证；P1 已实现并待真实 Docker/MySQL/Neo4j 环境端到端验证。
> 本文依据当前代码、交易闭环和项目 README 整理；没有把未验证的外部能力描述为已实现。

## CAPABILITY

当前项目已经能够演示多商家订单从购物车到签收、以及未发货全额退款。下一阶段的目标不是堆叠接口，而是把它发展为**可被商家运营、可被买家稳定使用、可被运营人员追溯**的商城后台：订单在失败、重复回调、超时和服务重试时仍保持一致；商家可维护商品和履约；买家可管理地址与售后；平台能够审计库存、优惠和资金状态。

| 可靠性 | 关键写命令幂等、库存/支付/售后行锁、订单 Outbox、带 HMAC-SHA256 请求体签名的可配置 HTTP Webhook、过期/重试任务、基础指标；网关将受格式约束的 `X-Correlation-Id` 透传给下游服务；买家/商家订单及售后时间线采用安全投影，不回传 Outbox 错误、内部载荷或操作主体 | 消费者去重验收、集中链路追踪与告警 |
| 运营 | 前向 SQL、带版本/校验记录的 MySQL 迁移脚本、健康检查和 Smoke Test 脚本、MySQL 一致性逻辑备份与 SHA-256/压缩完整性校验脚本（仅接受绝对归档路径与单行有效摘要） | 真实恢复演练、告警仪表板、压测、灰度与回滚 |

## 固定约束

- 保持 Java 8、Spring Boot 1.5.9、Spring Cloud Edgware 和既有 Neo4j 数据，版本升级另立专项。
- 交易数据仍以 MySQL 为准；商品目录继续归 `own-product`，库存归 `own-inventory`。
- 不新增前端、真实支付、真实物流或 OAuth；JWT 为默认网关认证模式。
- 写操作的演示身份头和 `Idempotency-Key` 仍是现阶段接口约束；它们不能被宣传为生产鉴权。
- 数据库变更只增加新的前向迁移脚本；不修改已发布的初始化脚本。

## 分期计划

### P0 — 交易可靠性补强（应优先于新增业务）

**当前代码状态：已实现，待 Docker/MySQL/Neo4j 真实依赖环境端到端验证。**

**用户结果**：重复请求、支付回调、库存竞争和超时订单不会产生重复扣减或永久占用。

| 工作项 | 服务 | 交付与验收 |
| --- | --- | --- |
| 通用幂等记录 | common、inventory、order、promotion、settlement | 新增请求指纹、作用域、结果快照和过期策略；同一 actor/路由/key 重试返回第一次结果，不同请求体返回 409；服务间库存/优惠券写调用按订单或售后业务键复用下游幂等键 |
| 库存并发与过期任务 | inventory、promotion | 悲观锁或可重试乐观锁；定时释放过期库存预占与优惠券占用；并发测试证明库存不为负、一次预占只释放一次 |
| 订单超时关闭 | order | 只关闭 `PENDING_PAYMENT`，释放库存与券，写事件；支付与关闭竞争有确定胜者 |
| 事务外盒 | order、promotion、settlement | `ord_event` 扩展投递状态、尝试次数和错误；事务提交后异步投递，消费者按事件 ID 去重 |
| 价格重校验 | order、product | 下单重新读取商品可售状态/价格，订单项保存不可变快照；价格变化的错误语义固定为 409 或 422 |
| 可观测性 | 全部交易服务 | 网关生成或校验后透传的关联 ID、结构化日志、失败计数、预占数量和 outbox 堆积指标；关联 ID 只接受长度不超过 100 的 `[A-Za-z0-9._:-]`，异常输入改用服务端 UUID |

已落地的第一版包括：24 小时成功响应幂等记录（记录创建、完成与失败释放均经独立事务保存）、库存悲观锁、15 分钟库存/优惠券预占与订单超时任务、下单前商品快照重校验、订单 Outbox 字段及禁用投递器、关联 ID 透传，以及 `trade.outbox.pending`/`trade.outbox.failed` 本地堆积指标。模拟支付成功、失败及整单退款会先锁定同一支付单，避免不同回调并发推进该支付状态；已取消的订单拒绝迟到支付回调，正常已支付订单仍可安全重放该回调。优惠券占用在到期或其自身更早失效时由本地扫描任务释放。真实 workflow/send 适配器仍在后续适配范围，不能宣称已完成外部投递。

**状态/不变量**

- 一个业务命令只产生一次可见状态转换。
- 库存关系始终满足：`available >= 0`、`reserved >= 0`、`sold >= 0`。
- 订单被关闭后不得支付成功；支付成功后不得被超时任务关闭。
- 订单事件持久化与订单状态更新同属一个本地事务。

**准备度**：可以直接实现，不需要产品决策。

### P1 — 商家可运营与买家可下单

**当前代码状态：已实现，待真实 Docker/MySQL/Neo4j 环境端到端验证。**

**用户结果**：商家能够维护可售商品和库存，买家不再依赖手写收货地址或人工创建演示数据。

| 工作项 | 服务 | 交付与验收 |
| --- | --- | --- |
| 商品 SKU 与可售状态 | product、inventory | `Product` 直接作为 SKU；商家只能编辑自己的 SKU；下架 SKU 不可加购/下单 |
| 地址簿 | user-party 或 order | 买家 CRUD 地址、默认地址与删除保护；默认地址写操作按买家 guard 行加悲观锁；下单快照地址；无地址下单返回 422 |
| 商家订单工作台 API | order | 按商家、状态、创建时间分页查询；不能读取其他商家订单或买家地址以外的无关数据 |
| 库存调整与审计 | inventory | 入库、出库、盘点差异、理由和操作人；不能绕开订单预占直接修改已售量 |
| 低库存预警 | inventory | 商家按自有 SKU 设置启用状态和非负阈值；商家及 SYSTEM 查询当前低于或等于阈值的库存。当前是实时读模型，不表示已通知外部渠道 |
| 商品搜索与筛选 | product | 名称、分类、商家、上下架和分页；查询接口不可拼接未经校验的 Cypher |
| 运费规则（简化） | order | 固定运费或按商家门槛免运费，费用在试算和订单中快照 |

**已锁定实现**

- 地址归 `own-user-party`，订单只保存地址不可变快照；新试算和下单必须传 `addressId`，自由文本地址返回 `422`。`buyer_address_guard` 为每个发生地址写操作的买家持有一行锁，确保始终至多一个默认地址。
- 运费为每商家固定金额，可选商品金额免邮门槛；未配置为 0，优惠券不抵扣运费。
- 商家工作台默认 20 条、最大 100 条；只显示本商家子订单和该订单的收货地址。
- P1 写接口继续复用 P0 的身份头与幂等约定；这仍不是生产鉴权。

**数据模型**

- `Product.skuCode`、`specification`、`saleStatus`
- `buyer_address`
- `inventory_adjustment`
- `merchant_freight_rule` 及订单运费快照字段

### P2 — 售后与履约闭环

**当前代码状态：基础状态机、订单项历史数量约束、审核逾期本地提醒、人工物流轨迹、自动收货，以及本地模拟的部分退款/退货库存回补已实现；真实依赖环境验证仍待完成。**

**用户结果**：买家可在规则内发起售后，商家可审核并确认退货收货，平台可追溯每件商品的去向；系统使用独立账本模拟部分退款，退款成功后售后单进入 `REFUNDED`。

| 工作项 | 服务 | 交付与验收 |
| --- | --- | --- |
| 售后单 | order、file、inventory 子域 | 已支持仅退款、退货退款、同 SKU 同数量换货与最多 10 份买家举证材料；换货在商家验收退件后进入待发货，商家填写替换件物流后进入 `EXCHANGE_SHIPPED`，仅原买家确认收货后才进入 `EXCHANGED`。举证文件必须先由同一买家创建为归属文件并提升为正式存储；不支持跨 SKU 或不同数量换货 |
| 部分退款 | settlement、inventory、after-sale | 按订单项计算；退款额度在支付单锁内核算，独立售后退款账本按售后单去重；库存仅在商家确认收到退货后、库存行锁内按商品去重回补。`REFUND_PENDING` 的本地派发失败会定时重试；当前不恢复整单核销券 |
| 售后审核流 | workflow、after-sale | 买家申请 → 商家审核 → 买家寄回 → 商家收货 → 退款；买家可仅在 `APPLYING` 撤销申请为 `CLOSED`，不会触发退款、库存或物流动作；每次迁移记录 actor、原因、凭证 |
| 物流轨迹 | order、after-sale | 已支持买家和所属商家读取经订单归属校验的物流轨迹；商家可为自有已发货子订单人工追加轨迹，并在买家签收前修正物流公司与单号；修正不重置原发货时间。第三方物流仍仅通过可替换适配器接入 |
| 自动收货 | order | 默认发货 7 天后每小时扫描并自动签收；有活跃售后单的子订单跳过，时限与扫描频率可配置 |

**开放决策**

1. 第一版默认将子订单优惠按申请商品金额比例分摊，运费不参与部分退款；最终结算实现前仍可调整。
2. 当前已实现“仅退款 + 退货退款 + 同 SKU 同数量换货”的申请、审核与退货物流状态机；跨 SKU、不同数量换货及逆向物流渠道仍不在本阶段范围内。
3. 商家审核超时默认在 48 小时后写入本地提醒事件，每 24 小时最多一次；不自动同意或拒绝，也不伪造外部通知送达。

**准备度**：售后单表、角色隔离、状态机、事件记录、审核提醒、人工物流轨迹、自动收货、模拟售后退款账本、退货库存回补及受控举证文件元数据已经接通。`08-after-sale-refund-ledger.sql` 被结算与库存服务使用，`16-owned-file-object.sql` 与 `17-after-sale-evidence.sql` 为新增的前向迁移；它们仍不是支付渠道退款、私有对象存储或真实物流验收。

### P3 — 生产化安全、支付与运营

**用户结果**：系统可在受控环境接入真实身份、支付和运营流程，出现异常可以审计和恢复。

| 工作项 | 服务 | 交付与验收 |
| --- | --- | --- |
| 认证授权 | gateway、user-party、common | 匿名 `POST /user/api/v1/auth/registrations` 可幂等创建仅 BUYER 的图谱账号（网关转发前后路径均受测试覆盖）、BCrypt 登录、短效 HS256 Access JWT、Refresh Session 轮换/登出撤销/过期清理、上一把密钥验签窗口、买家/商家可使用幂等的 `/user/api/v1/account/sessions` 撤销自己全部 Refresh Session，且服务端复核 JWT 用户与持久化主体归属、`ROLE_BUYER`/`ROLE_MERCHANT`/`ROLE_SYSTEM` 身份选择。仅 SYSTEM 可调用幂等的 `PUT /user/api/v1/system/accounts/{loginUserId}/merchant-role`：持久关联 `ROLE_MERCHANT` 并撤销目标账号全部 Refresh Session；`PUT /user/api/v1/system/roles/{roleId}/functions` 校验角色与功能存在后以图谱 `MERGE` 追加权限，不重复创建边。`/user/api/v1/account/profile` 仅允许买家/商家修改姓名、邮箱和电话；密码修改失败也复用账户锁定保护。Compose 仅暴露网关，网关替换外来 `X-Actor-*` 与内部令牌，并以至少 32 字节的 `INTERNAL_SERVICE_TOKEN` 向业务服务证明边界，服务边界过滤器拒绝直连伪造身份头。短信/邮箱验证、OAuth、工作负载身份与更细粒度资源策略仍待完成 |
| 支付适配器 | settlement | 渠道下单、验签、回调重放防护、退款、对账差异处理；模拟适配器仍保留用于测试 |
| 商家资金 | settlement | 应收、平台服务费、结算周期、提现申请与付款对账；与订单/退款保持可核对 |
| 数据迁移与运维 | 全部 | 已提供前向 SQL、Compose 挂载静态校验和 `scripts/apply-migrations.sh`（版本与 SHA-256 记录）；消息客户端仅将统一响应包 `data=success` 视作已受理，避免 HTTP 成功掩盖业务失败。备份恢复演练、监控告警、集中日志、分布式追踪、灰度与回滚仍待完成 |
| 合规与风控 | gateway、user-party、order | 订单服务已对完整地址快照读取写入不含个人信息正文的本地访问审计，并对该审计元数据提供可配置保留期；登录失败元数据会在保留期后清理且不会清除活跃锁定；网关已启用按来源 IP 的单实例内存限流。个人信息脱敏、全量数据保留策略、共享限流与防刷券/刷单规则仍待完成 |

**准备度**：需支付渠道、商家结算政策、隐私与账号体系的业务授权，不能直接实现。

## 非目标

- 不在 P0/P1 自动引入前端、直播/拼团/秒杀、推荐算法、跨境税务、仓配管理或多币种。
- 不将目前模拟支付、演示身份头或人工物流描述为真实生产集成。
- 不把当前的本地模拟部分退款、演示身份头或库存回补账本表述为真实支付渠道、财务结算或生产售后政策。
