## 已复现的问题

订单与结算的部分客户端只检查 HTTP 状态，或直接读取 `data`。HTTP 200 携带 `status=409` 时，调用方仍可能继续扣库存、核销券、确认支付、写商家应收或将退款通知当作成功。

## 当前响应契约

响应封套的唯一所有者仍是 `own-common` 的 `Resp`。新增 `TradeResponse.requireSuccess` 供本次四个交易客户端复用，不改请求路径、身份头、幂等键、正常业务参数或正常响应数据。

1. HTTP 状态必须为 2xx，响应体必须存在。
2. `status` 必须是 `Resp.status` 对应的整数，且处于 200–299；不将字符串、布尔值或小数强转为成功。
3. HTTP 失败、空体、缺状态或非法状态均不能视为已受理；非法封套向上报告 502。
4. 封套明确给出 4xx/5xx 时保留其状态，消息只记录固定操作名和状态码，不复制未知下游消息、凭据或业务正文。
5. 通过封套检查后，各客户端继续执行已有数据投影校验；本次不把封套成功当作实际落库、完整事务或跨服务一致性的证明。

| 消费者 | 纳入检查的路径 | 拒绝失败后不应发生的推进 |
| --- | --- | --- |
| `InventoryClient` | 预占、确认、释放、整单退款回补、售后退款/换货 | 不得因假成功继续核销券或确认父订单 |
| `CouponClient` | 试算、预占、核销、释放 | 不得使用失败封套中的优惠数据，或将未完成核销/释放当成完成 |
| `SettlementClient` | 售后退款派发 | 不得将失败封套当作已受理；沿用订单侧待退款记录及现有重试行为 |
| `OrderClient` | 可支付金额、商家结算明细、付款/整单退款/售后退款回调 | 不得把失败回调当成订单已确认，进而写应收或完成结算退款 |

原有测试中没有 `status` 的模拟成功响应已同步改成当前 `Resp` 封套；缺状态的响应改由专门失败测试覆盖，不留宽松回退。原有 201 成功响应、数据读取和稳定业务幂等键仍通过测试。

## C2 后续实现与证据边界

上述 09:03:31 的 404 项结果是响应契约阶段的历史证据，不能单独证明持久恢复。随后已实现结算持久意图、订单支付屏障、权威事实查询及恢复任务，并新增迁移 39；最终 09:33:50 全量 `verify` 为 444 项、失败/错误/跳过均为 0。新增 H2 仅用于测试，不改变生产存储选型。

后续实现覆盖：

1. 结算侧持久操作意图及本地完成记录：同一付款/动作只有一个业务效果，失败提交不能丢失恢复依据；不能仅加一个内存重试器。
2. 订单侧持久推进与取消/超时屏障：已开始确认支付但库存/券仅部分完成时，不能继续当作普通未支付订单释放资源。
3. 由库存、券、订单各自提供当前动作的权威事实，结果不确定时先核对业务键、归属、数量/金额及状态；HTTP 响应缓存不是独立落账证明。
4. 按确认事实恢复，不能恢复的情形进入明确待人工对账状态；不清除或自动解锁 `PROCESSING`，不更换幂等键制造第二次效果。
5. 本地故障注入覆盖模拟远端响应丢失、实际 H2/JPA 提交失败、重复投递及受控取消/发货交错；重建服务对象不是实际进程重启，未执行真实跨服务或 MySQL 故障注入。
