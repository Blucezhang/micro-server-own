# 支付与整单退款持久恢复

更新：2026-10-24。范围为代码、本地测试与打包；没有运行真实依赖、访问生产数据或执行 MySQL 迁移。

## 问题与当前实现

支付原先依次操作库存、券、订单和结算账本，远端生效后响应丢失或结算提交失败会留下分叉。整单退款有相同风险。本次保留既有 API、业务键和资金含义，不把多个本地事务称为分布式原子提交。

| 事实所有者 | 持久依据及恢复规则 |
| --- | --- |
| 订单 | `OrderPaymentGuard` 在独立事务中锁父订单、保存开始时间与尝试次数；之后才写库存/券。支付开始后取消及超时关闭不能释放资源；完成与订单本地状态同事务保存 |
| 库存/营销 | 只读内部接口返回当前订单绑定事实；恢复核对订单、商家/买家、SKU、数量或优惠金额。已完成的不重复 POST，可继续的沿用原业务键，缺失/冲突不能猜成功 |
| 结算 | `SettlementRecoveryJournal.begin` 在任何远端查询/写入前独立提交意图；付款/退款、应收及 `COMPLETED` 标记同事务提交。失败仍留 `PENDING`，重试先核对订单权威快照 |

两个恢复 worker 每次扫描最多 50 条待处理记录，逐笔记录失败。达到尝试上限进入 `RECONCILIATION_REQUIRED`，不会因提高上限自动复活人工状态。恢复调度器与现有后台任务分开，避免恢复请求阻塞所有定时任务。

已有 HTTP 幂等 `PROCESSING` 不删除、不改键、不自动解锁。事实足够时不重复调用已完成写入；事实不能确定时保留待处理，不伪造成功响应。整单退款仍沿用券释放/恢复语义；释放后当前绑定为空，不代表能证明过去哪次退款已执行。售后部分退款不恢复整单券的既有规则不变。

## 内部只读入口

下列接口均要求内部令牌与 SYSTEM 身份，不是新的业务前台入口：

- 订单：`GET /api/v1/internal/orders/{orderNo}/recovery-snapshot`，仅返回订单号、买家、应付金额及付款/恢复状态。
- 库存：`GET /api/v1/internal/orders/{orderNo}/inventory/state`，返回当前预占/提交/退款状态与匹配所需字段。
- 券：`GET /sale/api/v1/coupons/internal/orders/{orderNo}/state`，只读取当前绑定。
- 结算：`GET /api/v1/payments/internal/recovery/operations?status=RECONCILIATION_REQUIRED`，指定合法状态查询最近最多 100 条记录。

人工排查先核对操作键、原付款、订单及资源事实，保留差异与日志，再另行授权修复。此版本没有人工改账、强制确认成功或解锁接口；历史没有恢复标记的订单也不自动推断远端结果。

## 迁移与部署约束

迁移 `39-payment-recovery.sql` 为订单增加支付屏障字段，为结算增加唯一业务键的恢复表和待扫描索引。恢复表不使用付款外键，避免独立意图事务等待外层持有的付款行锁。历史订单保持 `NONE`，仅表示没有新恢复证据，不表示历史远端从未生效。

36–39 均为前向迁移；本次未实际执行。上线需先备份并验证恢复、暂停交易写入、迁移并协调部署订单/库存/营销/结算。存在恢复中或待人工对账记录时，不能混跑/回退到忽略屏障的旧订单代码，不能盲删日志或将状态清为 `NONE`。

恢复客户端配置：`trade.http.connect-timeout-millis` 默认 3000；`trade.http.read-timeout-millis` 在订单默认 10000、结算默认 30000；均只接受 1–60000ms，禁止零值关闭超时。原 Outbox HTTP 客户端不在此次改动范围。
