# 未支付取消与超时关闭恢复

更新：2026-10-25。只做代码、本地夹具验证，不连接真实业务环境。

## 意图、屏障与完成

`OrderCancellationGuard` 在独立事务中锁父单、核对原买家或内部 SYSTEM，确认未支付且没有支付开始屏障后保存取消开始时间、原始原因与尝试次数。已确认的支付和取消不能互相抢占；远端释放前意图必须提交。

之后由 `OrderCancellationService` 锁父单并释放库存/券，最后将父子订单取消、取消完成标记和事件放在同一本地事务提交。任一远端失败或本地提交失败，取消意图仍存在；支付资格和支付确认拒绝该订单继续付款。公开订单状态枚举不变，内部恢复字段不暴露为买家资料。

首次调用沿用原资源释放键；恢复时先核对库存所属订单、SKU、商家、数量和状态，已 RELEASED/EXPIRED 不重复写，仍 RESERVED 则使用原键释放，已提交或事实不匹配不得猜成功。券继续复用原释放键；当前绑定为空不是历史成功证据，遇到不确定 HTTP `PROCESSING` 不自动解锁。

`OrderCancellationRecoveryScheduler` 每批最多 50 条 PENDING，使用既有独立恢复调度器，逐笔记录异常。达到尝试上限转 `RECONCILIATION_REQUIRED`，不因提高上限自动重启。恢复保留最初 BUYER/TIMEOUT 原因，超时恢复不会伪装成买家取消。到期扫描逐笔捕获异常，单笔失败不应中断其他候选。

## 只读排查

`GET /api/v1/internal/recovery/cancellations?status=RECONCILIATION_REQUIRED` 同时要求内部令牌与 SYSTEM；只允许 PENDING、COMPLETED、RECONCILIATION_REQUIRED，最近最多 100 条。投影仅包含订单号、订单状态、恢复状态、次数、原因，不返回地址或内部请求缓存。

排查顺序：确认支付与取消屏障、核对原订单资源事实及释放键、记录差异和异常日志、制定有授权的修复。此版本不含修改状态、清屏障、强制完成或解锁接口，不把待人工处理记录当作已恢复。

## 迁移与证据

新增前向迁移 41，历史开始时间/原因保持空、恢复状态 NONE、次数 0，不补造历史取消意图。暂停写入并协调部署；有取消中/待人工处理记录时不能回退到忽略取消屏障的旧代码。

`OrderCancellationPersistenceTest` 8 项实际 H2/JPA：部分释放失败、实际提交前失败、事件保存失败、次数上限、归属/时限、支付优先、超时原因保留、受控取消/支付交错。`TradeRecoveryFactsTest` 新增 3 项资源事实检查，内部只读控制器 2 项。SQLite 迁移夹具 3 项验证代表性既有状态与新行默认值；这些不是 MySQL 并发、真实重启或真实服务恢复证明。
