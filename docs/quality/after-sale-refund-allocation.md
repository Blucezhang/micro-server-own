# 售后退款应收冲减：规则、迁移与代码验收

规则由用户于 2026-10-24 确认。本项只验证代码，不启动或检查外部服务；没有执行 MySQL 迁移、真实请求或付款。

## 唯一事实与计算口径

- `own-order` 持有售后单归属，内部退款请求从持久售后单带出 `afterSaleNo / orderNo / buyerId / merchantId / amount`。缺少或无效 `merchantId` 的旧写入契约拒绝；不得按订单号挑选商家。
- `own-settlement` 持有付款、原应收和退款分摊事实。原应收 `gross_amount / merchant_amount / platform_amount` 不改写，不使用当前配置的分成比例重算历史。
- `pay_after_sale_refund` 同一行保存退款与商家、平台冲减额；不再另建一份可漂移的余额计数。新记录必须先完成 `APPLIED` 分摊才能持久化。原 `after_sale_no` 唯一业务键继续去重。

设原应收总额为 G、原商家应收为 M，已归属成功退款总额为 R、商家已冲减总额为 D，本次退款为 A：

```text
本次商家冲减 = round_half_up((R + A) × M / G, 2) − D
本次平台冲减 = A − 本次商家冲减
```

同时校验 `R + A <= G`、原分成守恒及既有累计冲减正确；付款维度仍校验所有成功售后退款（包括待对账历史行）不超过原付款。累计全退时必须精确还原 M 与原平台金额，不能因分次舍入多扣或少扣一分。

余额统一按“已结算原商家应收 − 对应已归属成功退款的商家冲减 − REQUESTED/PAID 提现”计算。待结算退款在原应收进入结算后体现净额；已提现后允许负余额，新收入先抵减待追偿额。整单冲销后原应收不再进入已结算余额，已记部分退款也不再额外扣一次。提现记录不删除、不恢复、不伪造追偿完成。

## 提交与重放

1. 先锁付款，再首次读取退款账本并校验买家；新退款再锁对应原商家应收。
2. 在原本地事务中读取该应收的已归属成功退款、计算本次分摊并保存一行完整退款。分摊不单独改写原应收，因此插入失败不会留下孤立冲减。
3. 只有本地提交后才向订单通知新退款成功。`allocateAfterSaleRefund` 要求既有事务；Spring 注入商家结算服务为必需依赖，不允许新退款跳过分摊。
4. 同业务键重放只复用原账本、重新通知订单；订单、付款、金额或已记录商家不符返回冲突。历史商家为空的重放保留待对账状态，不用新请求自动补归属。

仓储行锁声明和 Spring 事务代理已纳入代码测试；真实 MySQL 隔离、锁等待、死锁和跨进程故障仍未验证。
